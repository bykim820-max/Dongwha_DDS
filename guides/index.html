DDS 선적용 가이드

개발 지식이 없어도 됩니다. 기획서 · 화면 정의서 · 디자인 시안을 만들 때 DDS(Dongwha Design System) 규칙을 미리 적용할 수 있도록 만든 가이드입니다. 표와 템플릿은 그대로 복사해서 문서에 붙여 쓰도록 설계했습니다.

대상
기획자 · 디자이너 · PM 등 비개발자 직군
목적
UI 파편화 · 하드코딩 사전 차단 / "왜 이 컴포넌트인지" 이해 / 즉시 복사해 쓰는 표준 템플릿
근거 문서
design.md · button.md · input.md · navigation.md · writing.md · i18n.md · icons.md

시작 전 30초 요약 — 이 5가지만 기억하세요

  1. 색상 · 크기는 이름으로 부른다. #14BC62, 13px 대신 → Color/bg/interactive/primary, spacing/12
  2. 이모지를 아이콘 자리에 쓰지 않는다. 장바구니 · 사람 · 체크 이모지 대신 → 표준 라인 아이콘 이름(cart, user, check)
  3. 내용이 다르면 Tabs, 보기 방식만 다르면 Segmented. 헷갈리면 §1.1
  4. 오류 문구에는 반드시 "다음에 할 일"을 넣는다. "오류가 발생했습니다" 단독 금지
  5. 버튼은 동사로. 확인 · 예 대신 → 저장 · 삭제 · 거래처 등록

이 5가지는 개발 단계에서 자동 검사로 걸러지거나 리뷰에서 반려됩니다(§4). 기획 · 디자인 단계에서 미리 지키면 수정 왕복이 사라집니다.

1.1 내비게이션 한눈에 고르기

내비게이션은 "지금 어디에 있고, 어디로 갈 수 있는지"를 알려주는 장치입니다. 기획 중인 화면에서 아래 질문에 답해 보세요.

  1. Q1클릭하면 "서로 다른 내용"의 패널이 바뀌나요?Tabs
  2. Q2내용은 같고 "보는 방식 · 범위"만 바뀌나요?Segmented Control
  3. Q3지금 페이지가 "몇 단계 깊이"에 있는지 보여주고 싶나요?Breadcrumb
  4. Q4목록 데이터가 많아 "여러 페이지로 나눠" 보여주나요?Pagination
  5. Q5앱의 "전체 메뉴 이동"인가요?SNB (사이드 메뉴)
상황컴포넌트항목 개수 제한예시
서로 다른 콘텐츠 패널 교체Tabs2~7개 (8개 이상 금지)프로필 / 알림 / 보안
같은 콘텐츠의 표시 방식 · 범위 전환Segmented Control2~4개 (5개 이상은 Select)일별 / 주별 / 월별
현재 페이지의 계층 경로 표시Breadcrumb3단계 이하 권장 (최대 4)홈 / 주문 / 주문번호 #12345
대량 목록의 페이지 나누기Pagination—1 2 3 … 25

가장 자주 틀리는 것: Tabs vs Segmented.

Tabs = 서랍장. 서랍마다 다른 물건이 들어 있다. (프로필 서랍, 알림 서랍)

Segmented = 안경. 같은 물건을 다르게 보는 도구다. (일별로 보기, 월별로 보기 / 카드로 보기, 목록으로 보기)

디자이너 참고 — Tabs · Segmented · Breadcrumb는 현재 사양(문서)이 먼저 확정된 상태로, Figma 라이브러리 게시는 대기 중입니다. 라이브러리에서 검색해도 나오지 않으니, 게시 전까지는 이 가이드의 사양대로 그리고 "DDS Tabs 사양 준수"라고 시안에 명시하세요. 게시되면 컴포넌트 인스턴스로 교체합니다.

1.2 Tabs — 정보를 병렬로 나눠 담을 때

언제 쓰나요

  • 한 화면 안에서 성격이 다른 정보 묶음을 나란히 배치할 때 (예: 설정 화면의 프로필 · 알림 · 보안 · 결제)
  • 목록을 상태별로 나눠 볼 때 (예: 전체 / 진행 중 / 완료)

언제 쓰면 안 되나요

이런 상황이면대신 이걸 쓰세요
탭이 8개 이상 필요하다SNB(사이드 메뉴) 또는 Select(드롭다운) — 정보 구조 재검토
탭 안에 또 탭이 필요하다 (2단 탭)금지. 정보 구조를 다시 설계
내용은 같고 보기 방식만 바뀐다Segmented Control
다른 페이지로 이동한다SNB 또는 링크 — Tabs는 같은 페이지 안의 전환

기획 시 지정할 옵션

옵션선택지기본값기획서에 쓸 때
모양 (variant)언더라인 / 알약(pill)언더라인특별한 이유 없으면 기본값
높이 (size)md(44px) / sm(36px)mdsm은 데이터 밀집 화면 + 데스크톱 전용. 모바일은 항상 md
정렬 (align)좌측 정렬 / 균등 분할좌측 정렬균등 분할은 모바일에서 탭 3개 이하일 때만
넘칠 때 (overflow)가로 스크롤 / "더 보기" 메뉴가로 스크롤데스크톱 고정 폭 화면은 메뉴 접기

상태별 주의사항 (기획 · 디자인 체크)

상태화면에서 이렇게 보입니다기획 · 디자인 시 주의
Default (기본)회색 계열 글자(Color/text/tertiary), 밑줄 없음기본 탭도 읽을 수 있는 대비여야 함 — 토큰 그대로 쓰면 보장됨
Hover (마우스 올림)글자가 한 단계 진해짐별도 디자인 불필요 — 시스템 규칙
Active/Selected (선택됨)진한 글자 + 굵은 글씨 + 초록 밑줄 2px색 하나만으로 선택 표시 금지. 색 + 굵기 + 밑줄 3중 표시가 규칙
Disabled (비활성)흐린 글자(Color/text/disabled)"왜 비활성인지" 툴팁이나 안내 문구를 함께 기획할 것

선택 밑줄이 왜 초록색인가요? 파란색으로 하면 키보드 포커스 표시(파랑)와 구분되지 않기 때문입니다. 선택 = 브랜드 초록, 포커스 = 파랑으로 역할이 나뉘어 있습니다. 임의로 바꾸지 마세요.

라벨 작성 규칙

  • 명사구, 1~2어절, 마침표 없음: 프로필 · 알림 · 보안
  • 동사형(설정하기) 금지 — 동사는 버튼의 것
  • 군더더기(알림 관리, 보안 페이지) 금지 — 알림, 보안이면 충분
  • 개수 배지는 숫자만: 알림 12 (999 초과 시 999+)
  • 영어로 바뀌면 폭이 최대 +80% 늘어납니다. 라벨을 짧게 유지하세요

추가로 기획서에 명시하면 좋은 것

  • 탭 상태는 주소(URL)에 남습니다 — 새로고침 · 뒤로가기 후에도 보던 탭 유지. 별도 요구가 없어도 이것이 기본 동작입니다
  • 탭 전환 시 데이터를 새로 불러오는 무거운 화면이면 기획서에 "수동 활성화(Enter로 확정)"라고 명시하세요

1.3 Segmented Control — 하나만 고르는 전환 토글

언제 쓰나요

같은 데이터를 다르게 보는 단일 선택 전용입니다. 항상 하나가 선택되어 있고, 다른 것을 누르면 즉시 바뀝니다.

  • 집계 구간 전환: 일별 / 주별 / 월별
  • 보기 방식 전환: 카드 / 목록
  • 언어 전환: 한국어 / English

언제 쓰면 안 되나요

이런 상황이면대신 이걸 쓰세요
선택지가 5개 이상Select(드롭다운)
여러 개를 동시에 켤 수 있어야 한다Checkbox 또는 필터 칩
켜기/끄기 하나뿐이다Switch
누르면 다른 내용의 패널이 바뀐다Tabs

상태별 주의사항

상태화면에서 이렇게 보입니다기획 · 디자인 시 주의
Default (비선택)연한 회색 트랙 위 투명 버튼, 회색 글자—
Hover미세한 배경 변화별도 디자인 불필요
Active/Selected흰 면 + 그림자가 올라오고 글자 굵어짐선택 표시에 브랜드색을 쓰지 않는 것이 규칙 — 화면에 여러 개 놓아도 시끄럽지 않게 하기 위함
Disabled흐린 글자항목 하나만 비활성도 가능. 이유를 툴팁으로

라벨 작성 규칙

  • Tabs보다 더 짧게 — 1어절: 일별 · 주별 · 월별
  • 그룹 전체에 "무엇을 고르는지" 이름이 필요합니다(스크린리더용). 기획서에 함께 적어 주세요 — 예: "집계 구간"

1.4 Breadcrumb — 현재 위치(Depth) 보여주기

언제 쓰나요

계층이 3단계 이상 깊은 구조에서, 사용자가 "지금 어디에 있는지"와 "상위로 가는 길"을 보여줄 때. 예: 홈 / 주문 / 주문번호 #12345

언제 쓰면 안 되나요

  • 2단계 이하의 얕은 구조 → 뒤로가기 버튼 하나로 충분합니다
  • 모바일 화면 → Breadcrumb를 줄여서 넣지 말고 숨기고 뒤로가기 버튼으로 대체합니다 (중간을 접어 2~3개만 남기면 위치를 오해하게 만듭니다)

꼭 지켜야 하는 규칙 (기획서에 그대로 반영)

규칙내용
깊이3단계 이하 권장, 최대 4단계
마지막 항목현재 페이지 = 링크가 아님. 진한 글자로만 표시 (자기 자신으로 가는 링크는 혼란만 줌)
구분자슬래시 / 고정. 화살표(>)나 아이콘으로 바꾸지 않음
4단계 초과 시중간을 … 메뉴로 접기 — 첫 항목과 마지막 2개는 항상 노출: 홈 / … / 주문 / 주문번호 #12345
긴 라벨말줄임(…) 처리 + 마우스 올리면 전체 문구 표시
항목 이름해당 페이지 제목과 같은 단어 사용 — 페이지 제목이 "주문 목록"이면 Breadcrumb도 주문(축약형은 사전 합의된 것만)

상태별 주의사항

상태표시
Default (중간 항목)회색 글자, 클릭 가능
Hover글자 진해짐 + 밑줄
Active (현재 페이지 = 마지막 항목)진한 글자 + 굵기. 클릭 불가
Disabled사용하지 않음 — 갈 수 없는 경로는 아예 표시하지 않습니다

1.5 Pagination — 대량 데이터 나눠 보여주기

테이블 · 목록의 데이터가 많아 한 화면에 다 보여줄 수 없을 때. 패턴은 4가지 중에서 고릅니다.

패턴이럴 때 선택예
번호형 (1, 2, 3, …)전체 페이지 수가 의미 있을 때 — 업무 테이블 기본관리자 주문 목록
이전/다음단순 순차 탐색만 필요할 때문서 상세 넘기기
무한 스크롤모바일, 피드형 콘텐츠알림 피드
더 보기 버튼페이지 개념이 약한 데이터검색 결과 추가 로드

업무 시스템 테이블은 번호형이 기본입니다. 무한 스크롤은 "몇 번째까지 봤는지"를 잃게 만들어 업무용 데이터 화면에 부적합합니다.

기획서에 함께 명시할 것

  • 현재 위치 표시: 11–20 / 총 248건 형식 (어디까지 봤는지 항상 보여줌)
  • 페이지당 행 수 선택지: 10 / 25 / 50 / 100 중 제공, 화면 성격에 맞는 기본값 지정 (일반적으로 25)
  • 페이지 이동 시 목록 상단으로 스크롤 여부

상태별 주의사항

상태주의
Default번호는 클릭 가능한 회색 글자
Hover배경 표시
Active (현재 페이지)진한 표시 + 클릭 불가. 색만으로 구분 금지 — 굵기 · 배경 동반

1.7 Button — 액션 버튼 고르기

버튼은 모든 화면에 나오고, 그래서 가장 자주 틀립니다. 틀리는 방식은 정해져 있습니다 — 초록 버튼이 여러 개 · "확인" 라벨 · 이동인데 버튼 · 빨간 삭제 버튼이 화면에 그대로.

버튼인가, 아닌가

  1. Q1누르면 "다른 페이지"로 가나요? (주소가 바뀜)링크
  2. Q2누르면 "지금 화면에서 뭔가 실행"되나요? (저장 · 삭제 · 열기)버튼
  3. Q3자리가 없어 아이콘만 두나요? (표 행의 편집 · 삭제)아이콘 버튼 + 툴팁
  4. Q4액션이 4개 이상 몰리나요?대표 1~3개 + "···" 메뉴
  5. Q5여러 값 중 고르거나, 켜고 끄나요?Segmented · Switch

한 줄 판별 — "누르면 주소창이 바뀌나?" 바뀌면 링크, 안 바뀌면 버튼. 모달을 여는 건 주소가 안 바뀌니 버튼입니다.

링크를 버튼처럼 보이게 하는 건 됩니다. 정의서에 "링크(버튼 스타일)"라고 적으세요.

위계 — 이 화면에서 제일 중요한 일 하나

색부터 고르지 마세요. "이 화면에서 사용자가 끝내야 하는 일"을 먼저 정하면 나머지는 따라옵니다.

  • 빨간 버튼은 화면에 바로 두지 않습니다. 목록의 "삭제"는 글자 버튼이고, 누르면 확인창이 뜨고, 그 확인창의 실행 버튼이 빨간색입니다.
  • 되돌릴 수 있는 삭제(휴지통으로 이동)는 빨간색이 아닙니다 — 회색 + "실행 취소" 토스트.

초록 버튼 1개 원칙의 예외 — 이 경우만 허용되고, 정의서에 이유를 적습니다.

1.8 Input — 입력칸 고르고 정의하기

폼에서 가장 자주 틀리는 것은 세 가지입니다 — 고르는 값을 입력칸으로 받기 · 자리표시(Placeholder)로 라벨 대신하기 · 입력 중에 오류부터 띄우기.

입력칸인가, 아닌가

  1. Q1값을 사용자가 새로 만들어 쓰나요? (이름 · 제목 · 메모)입력칸
  2. Q2정해진 값 중에서 고르나요? 2~4개라디오 (Option Group)
  3. Q3정해진 값 중에서 고르는데 5개 이상인가요?Select (드롭다운)
  4. Q4여러 줄로 쓰나요? (사유 · 비고 · 설명)여러 줄 입력 (Textarea)
  5. Q5날짜 · 기간인가요?날짜 선택 (Date Picker)
  6. Q6켜고 끄는 설정인가요?Switch

한 줄 판별 — "값을 만드는가, 고르는가?" 정해진 값을 입력칸으로 받으면 오타가 그대로 데이터가 됩니다.

Select · 여러 줄 입력 · 날짜 선택은 아직 DDS 문서가 없습니다. 정의서에는 이름만 적어 주세요. 개발에서는 브라우저 기본 요소에 입력칸 스타일을 입혀 씁니다.

이런 값이면이렇게 정의하세요
이메일 · 전화 · URL입력칸 + 종류 명시 (이메일, 전화) — 모바일에서 알맞은 키보드가 뜹니다
사번 · 우편번호 · 사업자번호 · 주문번호입력칸 + "숫자 키보드" 명시. 계산하는 숫자가 아니므로 숫자 전용 칸으로 만들지 않습니다 (앞자리 0이 사라짐)
금액 · 수량입력칸 + 단위(₩, 개) 명시
목록 검색표 위 툴바 왼쪽의 검색 입력칸 — 이 경우만 라벨 생략 가능

조건은 안내 문구로 먼저, 오류는 나중에. 입력 중인 사람에게 오류를 들이밀지 않습니다.

2.1 디자인 토큰이 뭔가요?

색상과 크기에 붙인 "공식 이름표"입니다. 시안이나 기획서에 #14BC62(색상 코드)나 13px(임의 수치)를 직접 적는 것을 하드코딩이라고 합니다. 대신 DDS는 모든 색 · 간격 · 모서리에 이름을 붙여 두었습니다.

직접 값 (하드코딩)토큰 (이름표)이름의 뜻
#14BC62Color/bg/interactive/primary"주요 액션 버튼의 배경색"
#DC2626 비슷한 빨강Color/text/danger"위험 · 오류를 알리는 글자색"
13px, 15pxspacing/12, spacing/16"간격 12, 간격 16" (8pt 그리드)

왜 이름으로 불러야 하나요?

  1. 다크 모드가 공짜로 됩니다. Color/bg/primary는 라이트에서 흰색, 다크에서 어두운 색으로 자동 전환됩니다. 오른쪽 위 다크 버튼을 눌러 이 페이지로 확인해 보세요.
  2. 브랜드 색이 바뀌어도 한 곳만 고칩니다. 이름을 쓴 화면은 자동 반영, 코드값을 쓴 화면은 하나하나 찾아 고쳐야 합니다.
  3. 접근성이 검증된 값입니다. 토큰 색상은 글자 대비(WCAG AA)가 이미 검증되어 있습니다. 임의 색은 "예쁘지만 안 읽히는" 화면을 만듭니다.
  4. 개발 단계에서 자동 검사로 걸러집니다. 시안에 하드코딩 값이 있으면 개발자가 어차피 토큰으로 바꿔야 하고, 그 과정에서 의도와 다른 색이 될 수 있습니다.

비유하자면 — 계좌번호(110-123-456789)를 외우는 대신 예금주 이름("동화 급여계좌")으로 저장하는 것과 같습니다. 번호가 바뀌어도 이름은 그대로니까요.

위 이름들은 현재 Figma 라이브러리에 실제 게시된 아이콘입니다. 게시된 세트는 아직 소수입니다 — 장바구니 · 경고 삼각형처럼 목록에 없는 아이콘은 아래 3번의 요청 절차를 따르세요.

왜 안 되나요?

  • 이모지는 기기 · 브라우저마다 다르게 생겼습니다. 같은 종 이모지가 iOS · Windows · 안드로이드에서 전부 다릅니다.
  • 색을 통제할 수 없어 다크 모드 · 상태색과 어긋납니다.
  • 스크린리더가 "웃는 얼굴 이모지"처럼 엉뚱하게 읽어 접근성을 해칩니다.

표준 아이콘은 어떻게 쓰나요?

  1. 아이콘은 얇은 라인(아웃라인) 스타일 한 세트로 통일되어 있습니다 (Lucide/Feather 계열). Figma 라이브러리에서 이름으로 검색해 사용하세요.
  2. 시안 · 기획서에는 이모지 대신 아이콘 이름을 적으세요 — 예: 아이콘: bell_on (알림)
  3. 필요한 아이콘이 라이브러리에 없으면 임의 이모지 · 타 스타일 아이콘으로 때우지 말고, 디자인시스템 담당자에게 같은 라인 세트로 추가 요청하세요.
  4. 예외: 금액의 ₩, 비율의 %처럼 문장 속 글자로 쓰는 기호는 허용됩니다. 아이콘 칩 · 버튼 · 메뉴 자리에만 금지입니다.

참고: 문서(기획서 · 위키)에 쓰는 이모지는 무방합니다. 금지 대상은 화면(UI)에 노출되는 이모지입니다.

SECTION 5

AI에게 DDS 화면 요청하기

5.1 왜 "DDS로 만들어줘"만으로는 안 되나요

AI는 눈치가 없습니다. 우리 서비스가 뭔지, 어떤 버튼이 몇 개여야 하는지, 문서에 없으면 그럴듯하게 지어냅니다 — 없는 색을 쓰고, 초록 버튼을 세 개 놓고, 이모지 아이콘을 답니다. 이건 AI가 규칙을 무시한 게 아니라, 우리가 규칙을 안 준 것입니다. 그래서 두 가지가 필요합니다.

  1. 규칙은 문서로 — DDS 저장소에 AGENTS.md가 있습니다. AI가 작업 전에 읽는 규칙(읽는 순서 · 절대 규칙 · 검증)이 여기 있습니다.
  2. 요청은 정의서로 — "거래처 목록 만들어줘"가 아니라, §1.6 · §1.7 · §1.8의 화면 정의서 템플릿을 채워서줍니다. 사람 개발자에게 주는 것과 같은 수준이어야 합니다.

5.2 준비 — AI에게 DDS를 읽히는 법

환경방법
DDS 저장소 안에서 작업 (Claude Code · Codex · Cursor 등)아무것도 안 해도 됩니다. AGENTS.md / CLAUDE.md가 자동으로 읽힙니다
다른 프로젝트(ITSM 등)에서 Claude Code로 작업개발자에게 DDS 플러그인 등록을 요청하세요 — /dds:init 한 번이면 팀 전체에 적용됩니다. 이후에는 그냥 요청하면 DDS 규칙이 자동 적용됩니다
다른 프로젝트에서 다른 AI 도구로 작업그 프로젝트의 AGENTS.md(또는 CLAUDE.md)에 AGENTS.md §5의 스니펫을 넣어 달라고 개발자에게 요청 — 1회만
채팅창에 파일 첨부로 작업아래 3개를 첨부하고 "먼저 읽어"라고 씁니다: design.md · AGENTS.md · 관련 컴포넌트 문서(button.md · input.md 등)

5.3 프롬프트 템플릿

그대로 복사해서 [ ] 부분만 채우세요. "예쁘게" · "깔끔하게" 같은 형용사는 넣지 않습니다 — AI가 자기 취향으로 채웁니다.

목록 + 필터 화면
DDS 규칙(AGENTS.md)을 먼저 읽고 아래 화면을 만들어줘.

■ 화면: [거래처 목록]
■ 유형: 목록 + 필터 (데스크톱 우선, 모바일은 보기만)
■ 열: [거래처명 · 담당자 · 상태(배지) · 최근 거래일 · 행 액션]
■ 필터: [상태(Segmented: 전체/거래중/중단) · 검색(거래처명)]
■ 헤더 액션: Primary [+ 거래처 등록] 1개, 보조 [내보내기]
■ 행 액션: 아이콘 [편집] [삭제] — 삭제는 확인창 "[거래처명]을(를) 삭제할까요?" → [취소] [삭제]
■ 빈 상태: "등록된 거래처가 없습니다" + [첫 거래처 등록]
■ 로딩: Skeleton 5행

제약:
- 토큰 이름만 사용, hex/px 직접 쓰지 말 것
- 초록(primary) 버튼은 화면에 1개
- 문구는 writing.md 패턴, "확인/OK" 금지
- 규칙이 문서에 없는 판단은 지어내지 말고 [미확인: 무엇]으로 표시
